# Unity 在线游戏故障诊断与复用实施手册

本手册把 TF_2D 的真实修复经验转换为其他 Unity 在线项目可复用的执行流程。项目细节和历史证据见 `tf2d-engineering-handbook.md`；架构、客户端、服务器、云端和性能专题仍以本仓库对应文档为准。

## AI 使用契约

1. 先读取目标项目的仓库规则、领域词汇、ADR、当前续接记录、测试和构建证据，禁止只凭聊天记忆接手。
2. 把信息分成四层：当前源码、当前自动化结果、实际部署状态、指定构建的真机观察。冲突时不得挑选最符合猜测的一层。
3. 修复前固定应用版本、Build GUID、设备/OS、网络、环境、Battle ID、Correlation ID、复现步骤和时间。
4. 同时列出不超过三个可证伪假设；每个假设必须指定同一帧需要记录的变量和真假判据。
5. 先增加观测，再调参数；先写能复现真实数量级的失败测试，再做最小修复。
6. 服务器权威、结算、资产账本、幂等和反作弊边界不得为修复表现问题而削弱。
7. 调试、压测、Excel 源文件和 secrets 不得进入 APK；验收构建结束后恢复仓库默认开关。

## 统一故障闭环

```text
用户可观察症状
  → 固定构建/设备/网络/战斗身份
  → 同帧记录输入、权威、预测、Transform 与 UI/暂停状态
  → 找到首个分歧帧
  → 用真实轨迹写确定性失败测试
  → 最小修复，不改规则和信任边界
  → 专项测试 + 完整回归 + 弱网/恢复/数据库门禁
  → 独立 acceptance 构建与 hash/签名/APK 隔离检查
  → 指定真机按固定步骤验收
  → 把根因、失败方式、修复、证据和剩余风险写回仓库
```

## 最小同帧运动证据

移动、瞬移、松杆残留和弹窗恢复问题至少记录：

- UTC 时间、Unity frame、unscaled time、帧耗时、`timeScale` 和暂停所有者。
- 玩家原始摇杆输入、归一化/量化结果、进入预测器的输入、零输入原因。
- 本地已发送/服务器已确认 input revision、最近移动方向、可靠命令 pending/applied sequence。
- 服务器 Tick、快照年龄/间隔、权威位置、预测起点/结果、纠偏候选和实际分支。
- `Transform` 应用前后位置、visible delta、prediction delta、外部 Transform 偏移。
- 是否玩家控制、ServerAutopilot、技能选择、死亡、恢复、失焦、单帧限幅。

默认只保留事件前后有限帧；满足“玩家控制、`timeScale > 0`、输入为零但 Transform 位移超过阈值”等条件时自动捕获。诊断器只陈述事实，不预先命名根因。

## 已验证故障模式与解决方式

### 松开摇杆后仍移动

常见根因是把连续方向当可靠命令队列，或某个 Android 生命周期分支没有发送零方向。

- 使用 latest-state 邮箱：只保留最新方向，不积压高频摇杆样本。
- `PointerUp`、`EndDrag`、`PointerCancel`、失焦、暂停、禁用、销毁、弹窗打开都统一 `ResetToZero`。
- 零方向也有递增 revision；旧租约、旧连接、倒序和重复序号必须拒绝。
- 玩家控制期本地表现应在一帧内停止，网络确认可以稍后到达。

验收：连续快速改变方向并松杆，角色位置和移动动画均保持；断网、切后台、弹窗和重连后重复。

### 松杆或技能选择结束后出现小幅位移

不要继续调插值阈值。先证明位移来自哪一帧、哪一分支。

TF_2D 的逐帧证据显示：输入为零，预测器进入 `stationary_reconciliation`；渲染位置与权威位置约差 1 单位，旧策略产生约 `0.12558` 的单帧移动。把同一轨迹写入测试后，旧代码得到与真机相同数量级，排除了网络 RTT、摇杆残留和外部脚本猜测。

可复用策略：

- `presentationPaused`：冻结画面位置。
- 玩家控制且零输入：`stationary_hold`，画面不移动，只记录权威误差。
- 玩家控制且有输入：预测并按有界规则纠偏。
- ServerAutopilot：才允许无输入时跟随权威位置。

服务器仍计算碰撞、伤害、刷怪、掉落和结算；该修复只改变表现策略，不把权威交给客户端。

### 技能选择结束后朝向被重置

视觉节点在弹窗/重建后可能恢复默认 `scale.x = +1`，而零输入分支不再更新朝向。

- 先写失败测试：最后逻辑朝左、当前视觉朝右、输入/位移均为零，期望仍朝左。
- 玩家控制且零输入时用最后有效 `LookDirection.x` 恢复符号。
- 有输入时使用输入朝向；Autopilot 使用权威渲染位移朝向。
- 只修改视觉节点 x，保留 y/z scale；只有真实移动才覆盖最后逻辑朝向。

### 战斗计时、摇杆、刷怪和技能全部停住

这通常不是四个独立 bug，而是场景启动状态机没有完成交接。

- 明确 `bootstrap → snapshot → initial offer → command applied → resume` 状态。
- 初始技能选择成功后必须等待权威应用，再关闭弹窗和恢复玩法时钟。
- `timeScale` 不能由多个脚本盲写；使用可追踪的暂停所有者。
- 场景尚未完成交接时禁止悄悄运行部分系统。

### 暂停/选技后大幅瞬移

不要在暂停期间继续累计“将来一次性追赶”的游戏时间或移动输入。

- 持久化玩法时钟，例如 `tick_schedule_origin` 与 `gameplay_paused_at`。
- 暂停期间不推进玩法 Tick，Worker 重启后也不补算暂停墙钟时间。
- 技能候选和暂停状态进入检查点；恢复同一战斗时重播同一候选。
- 普通快照与紧急快照分开，技能选择、终局等事件立即发送。

### 继续战斗却新建了一场

- `Start` 和 `Resume` 必须是不同语义。
- 恢复入口先做无副作用 active 查询和 reconnect；找不到时返回稳定错误，不得自动新建。
- 恢复成功必须保持同一 Battle ID、Tick、随机状态、内容版本和待选技能。

### 死亡后不结算或界面卡住

- 胜利、死亡、主动退出和超时产生不可变 Terminal Fact。
- 终局事实、结算、资产账本和 Outbox 在一个事务内写入并通过幂等键去重。
- 终局 UI 先显示；资产刷新异步执行，失败不得让结果界面永久等待。

### `persistentDataPath` 主线程异常

Unity API 不应在后台 Worker、构造器或字段初始化器调用。主线程先解析路径并传递普通字符串；后台只做纯序列化和文件 I/O。保存完成日志只能在真实写入成功后输出。

### Copy/Export 提示成功但没有有效报告

- 默认复制 compact JSON：环境、构建、战斗摘要、最新错误、有限 breadcrumbs 和事件计数。
- motion trace 只在异常触发时保存有限前后帧，不无限增长。
- 完整报告写文件并写后回读：比较字符/字节数和内容，只有验证通过才显示成功。
- 剪贴板内容过长时安全分段，每段有索引和完整性信息。
- 永不记录密码、令牌、私钥、完整连接串或可复用 ticket。

## 网络与通道判断

- HTTPS 用于登录、云存档、配置、探活、重连查询和最终结算查询。
- WSS 用于实时输入、确认、权威快照和可靠离散命令。
- Quick Tunnel 只适合有人值守的临时开发验收；地址不稳定、没有生产 SLA。
- 正式环境使用固定域名、受信任证书和持久 WSS；客户端不硬编码 VM IP。
- 移动端 VPN 可能改变路由和 RTT。必须同时测设备到入口 RTT、快照间隔、丢包/断线和服务器 Tick 延迟，不能仅凭 VPN 开关推断根因。

## 数据保护与历史清理

删除历史数据前固定顺序：

1. 生成逻辑备份、SHA-256 和 manifest。
2. 在隔离数据库实际恢复并核验迁移、战斗、结算和账本关键表。
3. 保留策略先 report-only，人工确认只命中过期、已终局中间数据。
4. 显式批准后才 apply；保留最终检查点、Terminal Fact、结算、账本、审计和未确认 Outbox。
5. `VACUUM ANALYZE` 让空间可重用；`VACUUM FULL`/repack 只在维护窗口评估。
6. 用相同负载复测数据库大小、CPU、p95/p99 和错误率，不能只凭“磁盘变小”宣称业务性能提升。

## 压测与容量结论的正确表达

一场虚拟战斗必须定义：独立身份、独立战斗和 WSS、输入/快照频率、真实敌人/技能/投射物/拾取/终局/结算/退出、战斗时长和稳定期。

每档并发记录：成功数、稳定时长、p50/p95/p99、错误分类、服务器 CPU/RSS/GC、数据库等待、网络、队列深度、Tick overrun 和重启/OOM。容量上限必须同时满足成功率、尾延迟、资源余量和正确性。

TF_2D 早期 4 vCPU/8 GiB Integration 阶段曾以 15 场为软上限、20 场为边界，30/50/100 断点失败；修正终局持续补位并完成 Stage33 候选后，同一规格镜像达到 30 场长稳、35 场余量薄、40 场资源红。两组数字对应不同源码/负载阶段，而且 Stage33 高级候选没有可由当前 `main` 重建的提交。它们都不是其他项目的容量数字，也不是 8 核线性翻倍承诺。

## AOI 选择

- 先用 Profiler 确认全遍历、候选构建、距离判断、序列化还是广播最贵。
- 低密度且实体高频移动时，维护复杂索引可能比全遍历更贵。
- 十字链表适合较低密度/有序邻域查询，但每 Tick 大量 x/y 更新有维护成本。
- 空间哈希适合高密度粗筛。TF_2D 只在敌人数达到阈值时用于投射物 broadphase，并保留低密度全遍历。
- 任何 AOI 替换都要比较候选数、查询耗时、维护耗时、总 Tick 时间和规范状态 hash；不能只比较查询函数。

## 发布门禁

- 后端架构/玩法测试、Unity EditMode、数据库迁移/恢复和弱网故障注入通过。
- 默认 development/staging/production 功能开关恢复关闭。
- acceptance APK 独立包名、ARM64、签名、Build GUID 和 SHA-256 可核对。
- APK 不含压测工具、测试结果、Excel 源文件或 secrets。
- 真机验证初始技能、计时、摇杆、刷怪、自动技能、升级、Boss、终局、恢复和第二局隔离。
- 连续变向松杆后保持；技能弹窗前后位置和最后逻辑朝向保持。
- Copy/Export 只有回读验证成功才提示成功。
- 备份完成真实恢复；清理只在恢复成功后执行。

## 可直接交给 AI 的任务模板

```text
你正在处理一个 Unity 在线游戏故障。先读取仓库规则、领域词汇、ADR、当前续接记录、
docs/online-game-incident-response.md 以及相关客户端/服务器/云端专题；不要依赖聊天记忆。

先固定 Build GUID、设备/OS、网络、环境、Battle ID 和复现步骤。
将事实分为当前源码、自动化结果、实际部署、真机观察四层。
只提出最多三个可证伪假设，并为每个假设定义同一帧必须记录的变量和真假判据。
先补观测并找到首个分歧帧，再用真实轨迹写确定性失败测试。
做最小修复，不修改玩法规则、服务器权威、结算、资产和反作弊边界。
完成专项测试、完整回归、弱网/恢复/数据库门禁，构建独立 acceptance 包并核验 hash/签名/APK 隔离。
最后让项目所有者按指定真机步骤验收，并把根因、修复、证据和剩余风险写回仓库。
```
