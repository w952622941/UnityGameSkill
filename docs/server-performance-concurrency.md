# 服务器降耗与并发承载能力优化方法调研

> 调研日期：2026-07-21
> 适用范围：通用 API、Unity 在线游戏的网关/大厅/房间/战斗服、WebSocket/gRPC/HTTP 服务。当前仓库未包含服务端源码、依赖清单或部署配置，因此以下是技术栈无关的完整方法地图；具体参数必须通过压测确定，不能照抄。

## AI 使用契约

本文件既是调研报告，也是可被其他项目 AI 直接读取的实施知识。AI 使用时必须遵守：

1. 先读取目标项目的服务端源码、依赖、部署配置、监控和压测资料；不存在的证据标记为“未确认”，不得把本文的可选方案描述成项目现状。
2. 先建立基线并定位瓶颈，再提出改动。至少记录稳定吞吐/在线连接、p95/p99、错误率、CPU、RSS、GC、数据库与网络指标。
3. 每项建议必须说明：证据、目标瓶颈、预期收益、风险、适用条件、验证办法和回滚办法。
4. 默认按 P0 → P1 → P2 推进；没有剖析证据时，不实施 GC 深调、内核调参、绑核、NUMA、分片、XDP 等 P2 改造。
5. 线程池、连接池、队列、缓存、批次、请求体、重试和超时必须有界；不得仅靠调大上限掩盖过载。
6. 不以平均延迟或短时峰值 QPS 宣称成功；使用相同硬件、数据和负载分布做前后对照，并检查长稳状态下的尾延迟与正确性。
7. 不以性能为由削弱鉴权、资产账本、幂等、结算正确性、数据保护或审计要求。
8. 修改生产基础设施、扩容、分片或一致性策略前，必须给出容量证据、故障演练与可执行回滚方案。

推荐给 AI 的任务入口：

```text
请读取 docs/server-performance-concurrency-research.md。先审计当前服务端的语言运行时、协议、存储、部署、峰值负载、SLO 和已有监控；建立可复现基线并定位前三个瓶颈。只选择有证据支持的 P0/P1 优化，逐项说明收益、风险、验证和回滚，实施后用相同负载复测。未经性能证据不要进入 P2 内核、NUMA、分片或协议重构。
```

## 结论与使用方式

提高并发的本质只有四类：**减少每次请求的 CPU/内存/磁盘/网络成本、提高资源复用率、削峰并限制过载、增加可并行容量**。建议优先级：

- **P0**：先做容量基线、修复热点与无界资源、缓存高频读、连接池、限流/背压/超时；通常风险最低、收益最大。
- **P1**：协议与数据访问优化、异步化、批处理、服务无状态化、水平扩缩容。
- **P2**：分片、内核/NUMA/GC 深调、专用硬件或协议；只在数据证明瓶颈位于该层时采用。

每项的“收益”是方向性预期，必须用相同数据集、相同硬件、相同请求分布的前后对照压测验证。核心验收指标统一为：最大稳定 RPS/在线连接数、p50/p95/p99 延迟、错误/超时率、CPU 核时/请求、分配字节/请求、RSS/连接、GC 暂停、磁盘 IOPS/等待、网络字节/请求、数据库 QPS/慢查询/锁等待、队列深度与单位请求成本。

## 1. 测量、容量与变更方法

1. **[P0] 建立真实负载模型**：按接口/消息类型、请求大小、读写比、长连接数、活跃率、峰谷和突发度建模。收益：避免优化错误对象；代价/风险：需要生产统计且须脱敏；条件：先有访问日志/指标；验证：回放流量分布与生产偏差、稳定吞吐、p99。
2. **[P0] 分层剖析 CPU、内存、I/O 与锁**：用采样 profiler、火焰图、分布式追踪和数据库执行计划定位热点。收益：找到最大成本项；风险：全量追踪本身会耗资源；条件：压测环境可复现；验证：热点占比、CPU/请求、分配/请求、阻塞时间。OpenTelemetry 明确建议衡量埋点的 CPU/内存成本并采用预热、多次测量；高规模系统常用采样并在 span 未记录时跳过昂贵属性计算。[OpenTelemetry 性能基准](https://opentelemetry.io/docs/specs/otel/performance-benchmark/)、[OpenTelemetry 埋点性能说明](https://opentelemetry.io/docs/concepts/instrumentation/libraries/#performance)
3. **[P0] 设定 SLO 与容量安全线**：以 p99、错误率和资源饱和点定义“最大稳定并发”，保留故障转移与突发余量。收益：防止追求峰值 RPS 而牺牲稳定性；风险：保留余量会降低平均利用率；验证：持续压测、阶梯压测、突发压测、单实例故障压测。
4. **[P0] 一次只改变一个变量并做 A/B 基准**：包括 JIT/缓存预热，至少多次重复，报告均值和尾延迟。收益：结论可归因；风险：周期更长；验证：置信区间、方差、回归阈值。[OpenTelemetry 基准指南](https://opentelemetry.io/docs/specs/otel/performance-benchmark/)
5. **[P1] 持续性能回归门禁**：CI 中固定基准、生产金丝雀比较资源/请求。收益：防止版本慢性退化；风险：共享机器噪声导致误报；条件：固定硬件/数据或统计消噪；验证：基准波动率、被拦截回归数。

## 2. 业务与算法层：先避免做无用功

1. **[P0] 删除重复计算与重复 I/O**：一次请求内记忆化、合并重复鉴权/配置/玩家数据读取。收益：直接降低 CPU 与下游 QPS；风险：请求内数据一致性；验证：调用次数/请求、CPU/请求。
2. **[P0] 降低算法复杂度与选择正确数据结构**：哈希索引替代线性扫描，增量聚合替代反复全量统计。收益：并发增长时延迟不陡升；风险：额外内存或写放大；验证：不同数据规模下耗时曲线、RSS。
3. **[P0] 只读取/返回必要字段**：分页、游标、字段投影、增量同步、兴趣管理（AOI）。收益：同时减少序列化、网络、内存和数据库成本；风险：接口复杂度、额外往返；适用：大对象/排行榜/背包/游戏世界状态；验证：字节/请求、行数/请求、序列化 CPU。
4. **[P0] 避免 N+1 调用**：批量查询、预取、服务端聚合。收益：显著减少 RTT 和连接占用；风险：过大批次造成内存峰值；验证：下游调用数/请求、p99。
5. **[P1] 预计算与物化结果**：排行榜、统计、配置派生结果在写入或后台计算。收益：读路径近 O(1)；风险：写放大、最终一致性和失效复杂；适用：读多写少；验证：读 CPU/QPS、数据新鲜度、重算耗时。
6. **[P1] 把非关键工作移出同步路径**：日志加工、邮件、分析、奖励通知走队列。收益：缩短连接占用和尾延迟；风险：最终一致性、重复消费、队列积压；条件：幂等、重试和死信；验证：同步 p99、队列年龄、消费失败率。
7. **[P1] 合并细粒度任务**：定时器分桶、tick 批处理、批量写日志/数据库/缓存。收益：减少调度、系统调用与事务成本；风险：增加等待延迟和单批峰值；验证：批大小、系统调用数、队列时延。
8. **[P1] 降低游戏服务器 tick/广播频率并事件驱动**：静止对象不更新，只向相关玩家发送变化。收益：降低战斗服 CPU 和带宽；风险：手感、同步精度、作弊校验；验证：CPU/房间、消息/秒/玩家、状态误差、客户端体验。
9. **[P1] 使用增量/差量与量化编码**：只传变化字段，坐标/角度按可接受精度量化。收益：降低带宽和编码成本；风险：协议复杂、累积误差；验证：字节/玩家秒、误差上限、重同步率。
10. **[P2] 近似算法与有界精度**：概率统计、采样、近似排行榜仅用于允许误差的场景。收益：大幅降内存/CPU；风险：业务结果不精确；验证：误差分布、成本下降；禁止用于货币、结算等强正确性数据。

## 3. 缓存

1. **[P0] 进程内缓存不可变/热点数据**：配置、路由、权限模板。收益：最低延迟且无网络 I/O；风险：多实例不一致、占用堆；条件：版本化/TTL/容量上限；验证：命中率、堆大小、陈旧读取率。
2. **[P0] 分布式缓存高频读**：玩家摘要、会话、排行榜页、查询结果。收益：卸载主库；风险：缓存穿透、击穿、雪崩和一致性；条件：明确缓存旁路/写穿策略；验证：命中率、回源 QPS、缓存 p99。
3. **[P0] 设置内存上限、TTL 与合适淘汰策略**：防止缓存把节点拖入 OOM；风险：淘汰导致回源风暴；验证：used/max memory、evicted_keys、命中率。[Redis 官方淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)
4. **[P0] 防穿透/击穿/雪崩**：空值短缓存、请求合并（single-flight）、热点互斥刷新、TTL 加随机抖动、提前刷新。收益：保护数据库；风险：等待者堆积或短时旧值；验证：单 key 并发回源数、过期时下游峰值。
5. **[P1] 多级缓存与 CDN/边缘缓存**：静态资源、补丁、公共配置和可缓存 API 前移。收益：省源站 CPU/带宽与跨地域 RTT；风险：失效和隐私配置错误；条件：正确 Cache-Control、版本化 URL；验证：边缘命中率、源站流量。
6. **[P1] 缓存紧凑表示并避免大 Key/热 Key**：拆分、压缩、热点复制或分片。收益：降低内存与单分片瓶颈；风险：更多 key/读取；验证：key 大小分布、分片 CPU/带宽偏斜。
7. **[P1] Redis pipeline/批量命令**：减少 RTT、系统调用和上下文切换，可显著提升单实例操作吞吐；风险：回复排队占内存，官方建议合理分批而非无界 pipeline；验证：ops/s、RTT、客户端/服务端内存。[Redis Pipelining](https://redis.io/docs/latest/develop/using-commands/pipelining/)
8. **[P2] 缓存分片/集群**：突破单机 CPU/内存上限；风险：重分片、热 key、跨槽操作、客户端需处理重定向；适用：已确认单节点饱和；验证：分片均衡度、迁移期间错误率。[Redis Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

## 4. 数据库与持久化

1. **[P0] 用执行计划治理慢查询**：为真实过滤、连接、排序建立合适索引；删除无效/重复索引。收益：减少扫描、CPU 和 I/O；风险：索引占空间并增加写成本；验证：扫描行数、buffer hit、执行时间、写 TPS。[PostgreSQL 索引官方文档](https://www.postgresql.org/docs/current/indexes.html)、[EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)
2. **[P0] 消除 N+1、全表扫描和无界结果集**：批量/连接查询、分页、列投影。收益：降低连接占用和网络；风险：复杂 SQL 可能产生巨大中间集；验证：SQL/请求、返回行/字节、p99。
3. **[P0] 数据库连接池并设置硬上限**：复用连接，避免建立连接和每连接内存成本；风险：池过大反而增加上下文切换与数据库争用，池过小排队；条件：用 Little's Law 和压测定容；验证：池等待、活跃/空闲连接、DB CPU。
4. **[P0] 缩短事务，避免在事务内网络调用**：降低锁持有和 MVCC 膨胀；风险：需重构一致性边界；验证：事务时长、锁等待、死锁、回滚率。
5. **[P0] 批量插入/更新与合并提交**：摊薄事务日志、网络和 fsync；风险：单批失败影响更大、延迟上升；验证：行/事务、WAL/行、写 TPS、p99。
6. **[P0] 维护统计信息与清理膨胀**：使优化器选对计划并回收旧版本；风险：维护本身消耗 I/O；条件：按写入模式调度/调参；验证：dead tuples、autovacuum 时长、计划估算误差。[PostgreSQL VACUUM](https://www.postgresql.org/docs/current/sql-vacuum.html)、[Planner Statistics](https://www.postgresql.org/docs/current/planner-stats.html)
7. **[P1] 读写分离/只读副本**：把允许延迟的读取移出主库；风险：复制延迟、读己之写失效、故障切换复杂；验证：主库 CPU、复制延迟、陈旧读率。
8. **[P1] 分区表与冷热分层**：裁剪扫描范围、让热点索引驻留内存、快速淘汰历史分区；风险：分区键错误、跨分区查询和运维复杂；适用：超大时序/日志/流水表；验证：分区裁剪、扫描块、维护时长。PostgreSQL 官方指出分区通常在表非常大时才值得，经验条件是表大于物理内存。[PostgreSQL 表分区](https://www.postgresql.org/docs/current/ddl-partitioning.html)
9. **[P1] 选择正确一致性和隔离级别**：仅在业务允许时减少串行化/同步复制成本；风险：幻读、丢失更新或短时不一致；验证：冲突/重试率、业务不变量审计。不能为性能牺牲货币、资产和结算正确性。
10. **[P1] 追加写、事件/日志批量落盘与数据归档**：减少随机写和热点表体积；风险：读取需聚合、恢复复杂；验证：写放大、IOPS、恢复时间。
11. **[P2] 水平分片**：按玩家/租户/房间等稳定键拆库，突破单库上限；风险：跨分片事务/查询、热点、迁移与全局 ID；条件：单库优化和垂直扩容已到限；验证：分片负载偏斜、跨片比例、扩容耗时。
12. **[P2] 按访问模式选择存储引擎**：KV、时序、列存、搜索引擎承担匹配负载；收益：避免通用数据库做不擅长的工作；风险：系统与一致性复杂度；验证：端到端成本、数据重复、恢复演练。

## 5. 并发模型、内存与运行时

1. **[P0] I/O 密集路径采用非阻塞异步 I/O**：少量线程承载更多连接；风险：阻塞调用混入会饿死事件循环，异步状态机也有开销；适用：大量慢网络/磁盘等待；验证：线程数、上下文切换、事件循环延迟、连接数。
2. **[P0] 有界线程池、队列和并发度**：任何连接、任务、批次、重试、缓存都设上限。收益：防止内存爆炸与排队崩溃；风险：过载时必须拒绝/降级；验证：队列深度/年龄、拒绝率、RSS。
3. **[P0] 消除锁热点**：缩小临界区、分段锁、读写分离、按房间/玩家 actor 化；风险：无锁结构难验证，可能增加内存；验证：锁等待、线程 runnable/blocked、扩核效率。
4. **[P0] 减少分配与复制**：对象池/缓冲池、复用序列化 buffer、切片/零拷贝、避免装箱和临时字符串。收益：降低 GC 和内存带宽；风险：池泄漏、生命周期错误、保留超大缓冲；验证：alloc bytes/op、GC 次数/暂停、RSS。
5. **[P1] 调整 GC 与堆上限**：选择吞吐/低延迟收集器，设置合理堆、代际和暂停目标。风险：参数依赖语言和存活对象结构，盲调会恶化；条件：先有 GC 日志；验证：暂停 p99、GC CPU%、分配速率、堆占用。
6. **[P1] 预热 JIT、连接池和热点缓存**：避免新实例首次流量抖动；风险：启动慢、预热冲击下游；验证：冷/热 p99、就绪时间。
7. **[P1] 限制线程和协程局部状态**：避免每连接一个大栈/大缓冲/大上下文；验证：RSS/连接、最大稳定连接数。
8. **[P1] CPU 密集任务隔离到专用池/进程**：路径搜索、压缩、加密、图片处理不阻塞 I/O reactor；风险：队列与跨进程复制；验证：事件循环延迟、专用池饱和度。
9. **[P2] CPU 亲和、NUMA 本地性和分片所有权**：减少跨 NUMA 内存和 cache line 争用；风险：部署复杂、负载不均；适用：高包率/高核数且 profiling 证明问题；验证：remote NUMA access、LLC miss、迁核次数。
10. **[P2] 使用更高效的实现/本地库/SIMD**：只替换被证明的热点；风险：可移植性、安全与维护成本；验证：微基准加端到端基准。
11. **[P2] 评估 `io_uring` 批量异步 I/O**：减少提交/完成 I/O 的系统调用与切换；风险：内核版本、库成熟度和排障复杂；适用：传统异步 I/O 已被证明为瓶颈；验证：syscalls/op、上下文切换、I/O p99。[Linux io_uring](https://docs.kernel.org/io_uring/)

## 6. 网络、协议与网关

1. **[P0] 连接复用与 keep-alive**：避免反复 TCP/TLS/鉴权握手；风险：空闲连接占 fd/内存，需空闲超时和最大请求数；验证：新建连接率、握手 CPU、RSS/连接。NGINX upstream keepalive 是每 worker 的空闲连接缓存，并不限制总连接数。[NGINX upstream keepalive](https://nginx.org/en/docs/http/ngx_http_upstream_module.html#keepalive)
2. **[P0] 设置请求/响应、header、帧、连接和空闲超时上限**：拒绝慢请求与超大载荷；风险：误伤慢网络玩家；验证：超限拒绝率、连接驻留时间、内存。
3. **[P0] 使用紧凑二进制协议并避免反复序列化**：Protobuf 等 schema 协议、内部透传已编码消息。收益：少字节、少解析；风险：可读性与版本兼容；验证：编码 CPU、payload 大小、兼容测试。
4. **[P1] HTTP/2 多路复用与头部压缩**：同连接并发交换、降低连接和 header 成本；风险：单连接并发流限制、流控、单连接故障域；验证：连接数、吞吐、排队。标准明确 HTTP/2 通过独立 stream 多路复用并压缩字段。[RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)
5. **[P1] gRPC 复用 channel/stub，长逻辑流酌情 streaming**：减少连接建立、负载均衡和 handler 创建；风险：长 stream 启动后无法再负载均衡，过多并发流会在客户端排队；验证：active streams、channel 队列、p99。[gRPC 性能最佳实践](https://grpc.io/docs/guides/performance/)
6. **[P1] 流控与背压贯穿客户端—网关—服务—队列—数据库**：快发送者不能压垮慢消费者；风险：传播等待可能超时；验证：in-flight、窗口、队列年龄、丢弃率。[gRPC Flow Control](https://grpc.io/docs/guides/flow-control/)
7. **[P1] 选择性压缩**：压缩大且可压缩的文本/状态，不压缩小包或已压缩媒体；收益：省带宽，代价：CPU/延迟；验证：压缩比、CPU/请求、端到端 p99。[gRPC Compression](https://grpc.io/docs/guides/compression/)
8. **[P1] 调整消息批次与合包**：减少小包和系统调用；风险：等待凑批增加延迟、TCP 层设置不当影响实时性；验证：包/秒、平均包长、延迟。
9. **[P1] TLS 会话恢复与硬件加速**：降低重复握手 CPU；风险：密钥/票据轮换、安全配置；验证：full/resumed handshake 比例、握手 CPU。
10. **[P1] 负载均衡采用最少连接/延迟或一致性哈希**：长连接和房间服务不能只按轮询；风险：粘性导致倾斜、节点摘除重映射；验证：实例 CPU/连接/房间数的变异系数。
11. **[P1] 静态资源/大文件由 CDN 或专用代理直接发送**：应用不搬运字节；风险：缓存权限和失效；验证：应用出口带宽、CPU、CDN 命中率。
12. **[P2] Linux RSS/RPS/RFS/XPS、IRQ affinity 与多队列网卡**：把包处理分散到 CPU 并改善 cache locality；风险：错误绑核会更慢、RPS 产生 IPI；条件：软中断/单队列确为瓶颈。内核文档指出 RSS 适合延迟敏感或接收中断成为瓶颈；已有每 CPU RSS 队列时 RPS 可能多余。[Linux 网络栈扩展文档](https://www.kernel.org/doc/html/latest/networking/scaling.html)
13. **[P2] QUIC/HTTP/3 评估**：改善高丢包/移动网络的连接迁移和独立流阻塞；风险：UDP 设施、CPU、可观测性和生态成本；条件：真实网络 A/B；验证：弱网 p99、重连成功率、服务器 CPU。[QUIC RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)
14. **[P2] 零拷贝与批量收发**：静态文件/代理转发评估 `sendfile`/`splice`，高包率场景评估 `sendmmsg`/`recvmmsg`；收益：减少复制与系统调用；风险：TLS、框架及可移植性限制；验证：CPU/GB、syscalls/s、吞吐。[Linux sendfile](https://man7.org/linux/man-pages/man2/sendfile.2.html)、[Linux splice](https://man7.org/linux/man-pages/man2/splice.2.html)、[Linux recvmmsg](https://man7.org/linux/man-pages/man2/recvmmsg.2.html)
15. **[P2] 网卡 checksum/segmentation/gather-receive offload**：让硬件或内核合并处理包，降低每包 CPU；风险：虚拟化、隧道、抓包和驱动兼容性；验证：软中断 CPU、包率、重传与错误。[Linux checksum offload](https://docs.kernel.org/networking/checksum-offloads.html)、[Linux segmentation offload](https://docs.kernel.org/networking/segmentation-offloads.html)
16. **[P2] XDP/AF_XDP 早期过滤或旁路数据面**：适合 DDoS 过滤、高包率 UDP/代理；风险：实现、运维和安全复杂度很高；条件：传统网络栈已成为明确瓶颈；验证：Mpps、每包 CPU、丢包率。[Linux AF_XDP](https://docs.kernel.org/networking/af_xdp.html)

## 7. 过载保护、可靠性与削峰

1. **[P0] 多层限流**：按 IP、账号、设备、接口、房间和下游预算采用令牌桶/漏桶；收益：恶意或突发流量不拖垮全局；风险：误限、公平性；验证：限流率、被保护资源饱和度、正常用户成功率。
2. **[P0] 准入控制与负载卸载**：接近容量线时拒绝新房间/低优先请求，而不是让全部请求超时；风险：局部失败显性化；验证：过载期成功吞吐、p99、拒绝原因。
3. **[P0] 端到端超时预算与取消传播**：客户端已离开/超时后停止下游计算；风险：超时过短；验证：取消后仍执行的工作量、超时率、资源回收时间。
4. **[P0] 重试必须有上限、指数退避、抖动和总预算**：只重试幂等/可安全重试操作；收益：避免重试风暴；风险：恢复变慢；验证：原始请求与尝试数比、重试成功率。
5. **[P0] 熔断、隔离舱和每依赖并发上限**：慢依赖不能耗尽全服务线程/连接；风险：熔断误判；验证：隔离池饱和、熔断时长、故障域。
6. **[P0] 优先级与公平排队**：登录/心跳/战斗关键消息优先，后台统计可丢弃/延迟；风险：低优先级饥饿；验证：各等级 p99、饿死时间。
7. **[P1] 消息队列削峰**：把允许异步的写入吸收到持久队列；风险：积压只是转移问题，必须按队列年龄扩容/降级；验证：队列深度、最老消息年龄、消费吞吐。
8. **[P1] 降级与陈旧数据服务**：过载时关闭昂贵推荐/排行刷新，返回缓存/较低刷新率；风险：体验和一致性；验证：降级期间核心成功率、数据新鲜度。
9. **[P1] 心跳和重连随机抖动**：避免整点、发布或网络恢复后同步洪峰；风险：故障发现略慢；验证：每秒连接/心跳峰均比。
10. **[P1] 负载感知的匹配与房间放置**：以 CPU、tick 延迟、房间权重而非只按数量分配；风险：调度复杂；验证：实例负载偏斜、tick overrun。

## 8. 架构与横向扩展

1. **[P0] 服务无状态化**：会话状态外置或可重建，实例可任意扩缩；风险：增加外部存储访问；适用：网关/API/大厅；验证：任意实例处理率、重启恢复、扩容时间。
2. **[P1] 按职责隔离资源**：网关、登录、大厅、匹配、战斗、聊天、分析分别扩缩，CPU 密集与 I/O 密集分池；风险：RPC 与运维复杂；验证：故障隔离、各池利用率。
3. **[P1] 水平扩容与负载均衡**：增加副本提高总容量；风险：共享数据库会成为新瓶颈、非线性扩展；验证：1/2/4/N 实例吞吐扩展效率。
4. **[P1] 基于领先指标自动扩缩**：除 CPU 外使用队列年龄、并发连接、房间数、匹配等待等；风险：指标滞后、抖动、冷启动；条件：预留最小副本和冷却期。Kubernetes HPA 可依据观测资源使用率调整副本，也支持事件驱动扩缩思路。[Kubernetes 工作负载自动扩缩](https://kubernetes.io/docs/concepts/workloads/autoscaling/)
5. **[P1] 资源 requests/limits 贴合实测并避免 CPU 节流**：提高装箱率同时保留峰值能力；风险：内存上限过低触发 OOM、CPU limit 引入尾延迟；验证：throttling、OOM、实际/请求比。Kubernetes 依据 requests 调度并通过 cgroup 执行 limits。[Kubernetes 容器资源管理](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)
6. **[P1] 拓扑分布与数据就近**：副本跨节点/区分散，访问同区缓存/数据库；收益：高可用并减少跨区延迟/费用；风险：过严约束导致调度失败。Kubernetes 拓扑分布可兼顾可用性和资源利用率。[Pod Topology Spread](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/)
7. **[P1] 预扩容与优雅扩缩**：活动前预热；下线先摘流量、等待连接/房间迁移或自然结束；风险：容量闲置、排空时间长；验证：发布/缩容断线率、冷启动 p99。
8. **[P2] 按玩家/区域/房间分片与一致性哈希**：把强交互留在同一节点，减少跨节点同步；风险：热点房间、迁移和容灾；验证：跨节点消息比例、分片倾斜、迁移中断。
9. **[P2] 多区域部署与边缘网关**：降低全球玩家 RTT、分散容量；风险：跨区一致性和成本极高；条件：明确数据主权与容灾模型；验证：区域 p99、跨区流量、RTO/RPO。

## 9. 日志、监控与后台任务自身降耗

1. **[P0] 禁止热路径同步日志和高基数字段**：异步批量写、限速、按级别关闭 debug；风险：崩溃时尾部日志丢失；验证：日志 CPU/带宽、队列丢弃率。
2. **[P0] 指标标签控制基数**：玩家 ID、请求 ID 不作指标标签；收益：避免时序库和 SDK 内存爆炸；风险：诊断粒度下降；验证：活跃时间序列数、监控成本。
3. **[P1] Trace 采样与批量导出**：保留错误/慢请求并按比例采正常请求；风险：遗漏稀有问题；验证：采样覆盖、SDK CPU/RSS。OpenTelemetry 提供比例采样以限制 trace 量。[OpenTelemetry Sampling](https://opentelemetry.io/docs/languages/js/sampling/)
4. **[P1] 日志压缩、轮转、保留与异地处理**：避免磁盘写满和与业务争 I/O；风险：检索延迟；验证：日志 IOPS、磁盘水位。
5. **[P1] 后台任务错峰、分片和限速**：报表、归档、缓存重建不与晚高峰竞争；风险：完成时间延长；验证：高峰资源占比、任务 SLA。

## 10. 资源与操作系统基础项

1. **[P0] 正确设置文件描述符、监听 backlog 和连接上限**：避免先撞系统硬限制；风险：只调大上限会把压力推到内存/下游；验证：accept/socket 错误、fd 使用率、listen drops。
2. **[P0] 防止 swap 抖动和磁盘写满**：设置内存水位、日志/临时文件配额、OOM 策略；风险：禁用 swap 后内存峰值直接 OOM；验证：major faults、swap in/out、磁盘水位。
3. **[P1] 使用适合负载的实例与本地 SSD/更快网卡**：在软件优化边际收益低时垂直扩容；风险：成本、单机故障域和供应限制；验证：单位吞吐成本、资源瓶颈迁移。
4. **[P1] 将临时文件、日志、数据库数据盘隔离**：减少 I/O 争用；风险：运维复杂；验证：各设备 util/await、业务 p99。
5. **[P1] 时间同步和单调时钟**：避免 TTL、超时、租约和性能统计异常；风险低；验证：时钟偏差、超时异常。
6. **[P2] 内核 TCP/UDP 缓冲、拥塞控制、端口范围按实测调优**：风险：内存乘以连接数，错误参数可能加重排队；条件：netstat/ss/eBPF 证明丢包、缓冲或端口耗尽；验证：重传、丢包、socket memory、端口使用。
7. **[P2] HugeTLB/大页按运行时与数据库官方建议评估**：可能降低 TLB 压力；风险：预留浪费、碎片和尾延迟恶化，不能默认开启；验证：TLB miss、RSS、p99。[Linux HugeTLB](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)
8. **[P2] NGINX/event-driven 代理参数按容量设置**：`worker_processes`、`worker_connections`、上游连接复用共同决定代理承载；风险：连接上限还受 fd 和上下游连接倍数约束；验证：active connections、accept error、worker CPU。[NGINX Core Module](https://nginx.org/en/docs/ngx_core_module.html)

## 10.1 HTTP 缓存与静态内容补充

1. **[P1] 正确使用 `Cache-Control`、验证器与条件请求**：用 `ETag`/`Last-Modified` 让未变化内容返回轻量验证结果；风险：缓存键、用户私有响应和 `Vary` 配错会泄露数据；验证：304 比例、源站字节与命中率。[HTTP Caching RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html)
2. **[P1] 允许时采用 stale-while-revalidate / stale-if-error**：后台刷新或故障时短时服务旧内容，避免同步回源惊群；风险：数据陈旧；适用：公共配置、非关键榜单和静态元数据；验证：回源峰值、陈旧年龄。[RFC 5861](https://www.rfc-editor.org/rfc/rfc5861.html)
3. **[P1] 静态压缩预生成**：提前产出 gzip/Brotli 版本，避免每次请求动态压缩；风险：构建物和缓存变体增多；验证：动态压缩 CPU、源站吞吐。

## 11. 常见“优化”陷阱

1. **不要只把线程池、连接池、队列和超时调大**：这通常只是把失败从“快速拒绝”变成“内存膨胀与长尾超时”。
2. **不要无证据微调 GC、内核参数或绑核**：先证明瓶颈位于该层，并保留回滚和前后基准。
3. **不要把缓存当数据库且不设上限**：必须定义权威数据源、失效、雪崩保护和内存淘汰。
4. **不要把重试当可靠性**：无预算的重试会指数放大故障；写操作必须先解决幂等。
5. **不要过早拆微服务/分库分片**：它们主要解决独立扩展和组织边界，同时会增加 RPC、序列化、一致性及运维成本。
6. **不要只看平均延迟或峰值 QPS**：用稳定运行期间的 p95/p99、错误率、资源饱和和单位请求成本判断。
7. **不要用压缩处理所有包**：小包、已压缩资源通常得不偿失；按大小、内容和 CPU 预算动态选择。
8. **不要牺牲资产/结算正确性换性能**：优化隔离级别、异步落库或最终一致性之前，先写出业务不变量与补偿/审计机制。

## 12. 推荐落地顺序（首轮 2–4 周）

1. 收集一周峰值负载，建立接口/消息/房间模型；在隔离环境做阶梯、突发、长稳和故障压测。
2. 找到 CPU、分配、慢 SQL、锁、下游调用和网络字节前十热点，按“影响 × 改造成本 × 风险”排序。
3. 给连接池、线程池、队列、批次、请求体、缓存、重试全部加可观测硬上限；补齐超时、取消、限流和降级。
4. 优化前三个热点：通常是慢查询/N+1、重复序列化或调用、缓存缺失/失效风暴、同步日志。
5. 复用连接、批量访问缓存/数据库、减少字段与广播范围；针对 Unity 实时服重点测 tick CPU、消息/玩家秒、房间倾斜。
6. 把允许最终一致的工作移到有界队列，按队列年龄扩容；保证幂等和死信处理。
7. 将可横向扩展服务无状态化，验证 1/2/4 实例扩展效率后再启用自动扩缩。
8. 只有 profiling 仍显示网络软中断、NUMA、GC 或单库存储达到上限，才进入 P2 内核调优、分片或多区域方案。

## 13. 针对本项目仍需补充的信息

要把本清单变成精确改造方案，至少需要：服务端语言/运行时及版本、网关和协议、数据库/缓存/消息队列、容器与云环境、现有实例规格、峰值在线与活跃比例、消息频率和大小、核心 SLO、压测报告、CPU/内存/GC/慢 SQL/网络指标。仓库当前没有这些材料，因此本文没有给出任何未经验证的线程数、连接数、缓存大小或内核参数值。
