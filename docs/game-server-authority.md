# 权威游戏服务器实施指南

服务器权威的含义是：客户端可以很流畅，但不能决定永久结果。服务器必须能够拒绝伪造事实、重复请求、旧连接和资源耗尽攻击。

## 服务边界

建议从可替换的模块化单体开始：

- 身份、会话和一次性连接票据
- 玩家存档读取与冲突处理
- 战斗票据、实时会话或回放验证
- 资产账本与幂等结算
- 配置发布与内容哈希
- Outbox、运营投影、风控信号和审计

早期无需为了“像大厂”拆成大量微服务。先保证数据库事务、协议和可观测性边界正确。

## HTTPS 与 WSS 的职责

- HTTPS：登录、配置清单、存档、资产、创建战斗、上传证据、查询验证/结算。
- WSS：实时输入、确认、快照、心跳、重连与终局通知。
- 生产实时战斗不要采用每 Tick 一次 HTTP 请求。
- Quick Tunnel 适合临时真机验收，不适合作为生产战斗通道。

连接票据应短期、一次性，放在安全握手字段而不是 URL 查询字符串；服务器存摘要，不存可直接复用的明文。每个战斗/玩家/连接都有租约，重连后轮换租约，旧连接立刻失效。

## 固定 Tick 与确定性核心

- 核心使用纯语言数据结构，禁止依赖 Unity 场景、物理和帧率。
- 固定 Tick，例如 20 Hz；数值采用整数或固定点。
- RNG 算法和取值顺序写入版本契约。
- 所有集合遍历、排序、序列化和舍入规则必须稳定。
- 客户端与服务器对同一票据和输入生成完全相同的黄金哈希；确定性测试没有“允许误差”。

一个真实故障来自配置传输：服务器把 3600 项方向表序列化成空对象，客户端退回本地默认表，双方从 Tick 20 开始分歧。修复不是放宽哈希，而是修正可序列化属性并加入跨运行时传输/黄金测试。

## 输入、队列和资源上限

- 单调递增序号；重复序号幂等，回退序号拒绝。
- 移动只保留最新状态；技能/复活/退出使用有界离散队列。
- 限制消息字节数、数组长度、JSON 深度、数值范围和每秒请求数。
- 拒绝 `NaN`、无穷大、非法枚举和超出单位圆的方向。
- 输入速率与模拟 Tick 解耦，慢客户端或恶意客户端不能拖慢房间循环。

## 状态、重连和终局

实时模式建议保存周期检查点。断线时按玩法选择：短期保留最后安全输入、角色停止、或服务器托管；策略必须确定且可测试。重连请求携带战斗 ID、最后确认 Tick 和新票据，服务器返回新租约及权威快照。

终局记录不可变：

- `(battleId, terminalType)` 只成功一次。
- 结算请求具有稳定幂等键。
- 重试 100 次仍只产生一笔资产变更。
- 主动退出、死亡、胜利和超时分别记录。

## 资产账本与 Outbox

不要直接执行 `balance += clientGold`。在同一数据库事务内：

1. 锁定或幂等读取战斗终局。
2. 根据服务器模拟/验证结果生成资产流水。
3. 插入唯一账本项并更新余额投影。
4. 写入 Outbox 事件。
5. 提交事务。

Outbox 消费者再更新数据仓库、运营后台、通知和风控。事件标记事实等级：`server_fact`、`provider_fact`、`client_claim`、`operator_action`。分析投影不能反向修改权威资产。

## 反作弊：验证事实，不迷信客户端外壳

已验证且可泛化的组合：

- 服务端签发战斗票据并固定版本、种子和规则。
- 客户端仅提交意图/证据，服务器重算伤害、掉落和结算。
- 短期令牌、租约轮换、序号、防重放和幂等。
- 速度、输入频率、战斗时长、资源增长和协议尺寸的硬限制。
- 关键配置哈希、回放检查点和首个分歧定位。
- 风险信号分级：先观察，再限制高价值行为，最后人工或多证据处罚。

代码混淆、APK 哈希、设备证明和系统完整性 API 只能提高攻击成本。不要把共享 HMAC 密钥放入 APK，也不要仅凭 IP、Root、模拟器或一次完整性失败永久封禁。

## 性能与发布

TF_2D 的服务端回放曾因 Debug 发布导致 2607 Tick 验证约 10.47 秒。切换 Release 并采用稀疏检查点重放后，在保持 130 个检查点和最终哈希一致的前提下，核心回放约 1.83 秒。可复用结论：

- 验收与生产必须使用 Release 构建测量。
- 优化前后必须比较完整结果和检查点哈希，而不仅是速度。
- 验证 Worker 使用租约、超时和幂等，崩溃后可以由另一 Worker 接管。
- CPU、内存、队列、证据大小和单战斗时长都要有界。

实时战斗容量优化继续读取 `server-performance-concurrency.md`。优先减少重复数据库读取、模拟器重建、对象分配、编码和锁竞争；不得未经确认就降低 Tick、快照/输入频率、刷怪或技能复杂度。容量测试必须在终局后持续补位，并把业务成功与 CPU/GC/数据库等资源门槛分别判定。
